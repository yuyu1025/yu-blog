软件工程师要解决的新一批问题

Oct 28, 2026

译文说明：本文译自 Katelyn Lesse（Anthropic 平台负责人）于 2026 年 10 月 26 日发布在 X 上的文章《The new set of problems for engineers to solve》。
原文链接：https://x.com/katelyn_lesse/status/2114542280535318557
版权归原作者所有，本译文仅供学习交流；如有出入，以原文为准。

很多软件工程师正在经历一场只能被称作「身份危机」的东西。工作本身变了太多。有人沮丧，也有人正过着人生中最快乐的时光。

我看到一件非常具体的事正在发生，它让我对未来一两年里「做工程」的样子异常兴奋——除非软件工程师把一些问题解决掉，否则 AI 根本无法创造出它本可以创造的惊人成果。这件事关乎存亡，而这恰恰也是最好玩的地方。所以，现在是个相当不可思议的时刻，适合做软件工程师。

多智能体系统正在制造这些问题

Agent 最初只是基础的人机环路聊天。后来模型越来越擅长在更难的问题上跑得更久，agentic 系统开始搬到云上。就在这个过程中，模型开始变得擅长协作，于是人们搭出了初步的多智能体系统：比如一个 orchestrator 为某个任务派生出若干 subagent；或者给 agent 派发执行之外的其他角色来提升结果，比如打分、当顾问，或者「做梦」（dreaming）。

现在，已经有人在构建真正了不起的多智能体系统，去攻世界上最难也最重要的问题——严肃的科研、发现、硬件设计。想象一下：数千个 agent，持续朝这些目标工作。随之而来的是一整套新的软件工程问题，而且已经冒头了。

基础设施需要演进，才扛得住更突发的负载。我们需要真正的认证与授权机制，来识别 agent、让它们彼此协作、让它们做该做的事，也阻止它们做不该做的事。面对不可信的代码和内容，安全与恰当的隔离至关重要。我们还必须有监控能力，并且在系统跑偏的时候能把它当场刹住。

模型会继续变好，这类多智能体系统会变得非常强大。但要想真正解锁这股力量，让世界敢于信任它去创造好的结果——比如治愈疾病，而不是坏的结果——软件工程师必须把这些题都解出来。

问题清单

一、基础设施需要演进

软件行业这些年一直建在 Kubernetes 上，而 Kubernetes 是为无状态、可复制的应用，或是一组编号稳定的有状态 pod 设计的。

Agent 完全是另一回事。它们本质上是隔离的、有状态的、单实例的工作负载。它们可能在两段工作之间闲置任意长的时间，而且大量时间都花在等工具、等模型推理、等其他 agent、等人类输入上。有些负载需要快速启动，有些需要避免浪费算力，还有些需要夸张到离谱的规模。

一批极优秀的工程师正在这个方向上猛推——比如 AI 基础设施公司在造新的文件系统和沙箱方案，Google 团队在做 Agent Substrate 这个新运行时。但还有一大堆东西没搞明白。

二、身份与访问

Agent 认证这块有题要解：当一个动作被执行了，怎么识别出是哪个 agent 干的。这块的好处是，微服务世界已经积累并打磨过一批积木，比如用短期证书而不是静态密钥来做 workload identity，现在大家开始把这些概念用到 agent 上。

Agent 授权的空间就开阔得多：你允许一个 agent 做什么？

很多 agent 是替人干活的，用那个人的身份和凭证去访问各种系统、执行各种动作。这里已经藏着一个问题：怎么分辨执行动作的是 agent 而不是本人。而在这种 on-behalf-of（OBO，代他人行事）的结构里，还有更深的问题，比如同意（consent）。如果一个多智能体系统要连着工作好几周，人类怎么才算「有意义地」批准了自己的 agent 能做什么？工具调用自动批准这类 agentic 平台功能有帮助，但要在高规模下真正做对，还需要更深一层的权限机制。

再往下是 agent 用自己的身份工作，这块解得更少；以及怎么把它套用到 agent 之间的协作上——一个 agent 该怎么信任另一个向它提要求的 agent？

三、安全与隔离

过去几个月，尤其是最近几周，漏洞出现的速度超过了行业打补丁的速度，而且很多出在大量系统所依赖的关键核心软件里。

现在再想一下：数千个常驻 agent 跑在这些核心软件之上，写着不可信的代码、读着不可信的内容。在这个世界里，那些没打上补丁的漏洞会危险得多。软件工程师最该做的事情之一，就是对「怎么加固这些软件」拿出创造力来——内核、浏览器、运行时、常用库。

多智能体系统还带来另一层麻烦。一个被攻陷的 agent，可以把注入的指令传给与它协作的其他 agent，而这些指令可能留在记忆里，让未来的 agent 不小心当真。爆炸半径（blast radius）于是变得非常现实：第一个 agent 被攻陷时，整个多智能体系统有多大一块处在风险之中？这种世界里，隔离变得重要——agent 应该在强隔离的沙箱执行环境里执行动作。关于这一点我之前写过一些（链接）。

四、监控与中止

最后，我们需要工具来确保这些多智能体系统朝着正确的方向推进，并且在它们没有的时候抓住它们、切断它们。

我们需要跨 agent 的 OTel 追踪，并且要确保一个 agent 永远无法修改自己的追踪记录，也无法修改别的 agent 的追踪记录。我们需要监控能够触发的 kill switch，能一次性真正停掉整个系统、切断它的凭证。

真正难的部分是：怎么知道系统正走错方向。善意而执着的解题，看起来可能非常像恶意行为——比如反复尝试访问一个不在白名单里的域名。

软件工程师应该感到兴奋

这段话是写给那些正陷入身份危机、觉得自己知识和技能不再重要的工程师的：

你和你的技能，可能正是这些题能不能被做出来、多智能体系统能不能解决世界上最难的那些问题的分水岭。你可以，也应该，往这些领域里深钻、学新东西、形成自己的判断。这个问题的空间里，有太多地方对新方案敞开着。

现在正是把技能拿去用的、极其令人兴奋的时刻。
