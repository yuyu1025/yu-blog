AI 智能体：从架构到收款的完整地图

Oct 28, 2026

译文说明：本文译自 silvan（@silvanrec）于 2026 年 8 月 20 日发布在 X 上的西语长文《AGENTES IA: LA GUÍA COMPLETA (monetiza hoy)》。
原文链接：https://x.com/silvanrec/status/2090280285623464099
版权归原作者所有，本译文仅供学习交流；如有出入，以原文为准。

有两个人，在同一个月里发现了 AI 智能体。

第一个花了好几周试各种 demo，刷「看这个 agent 能干什么」的帖子，却始终没搞懂下面到底跑着什么——function calling、编排、持久记忆。于是他永远停在营销层。第二个人想明白了一件事：一个智能体，技术上就是一个能访问工具、能保持状态的推理循环。于是他第一周就开始把它当基础设施往外卖。

差别不在天赋。差别在于，第二个人对架构的理解足够深，深到能给一个真实业务做诊断，而不是复述 YouTube 上的 demo。

这份指南是故意写得又长又硬的。如果你已经知道 LLM 是什么，却从来没在生产环境里搭过一个智能体，那你需要的不是一堆散装的工具清单，而是一张完整地图：架构、技术栈、该收多少钱、第一个客户去哪找，还有哪些技术错误会让你白白丢掉一个月。

收藏它。你会回来翻不止一次。

整份指南分六层，按「开始收钱之前所需的架构复杂度」从低到高排列；后面是常见技术错误，最后是按类别分的工具栈。

技术要点速览

  • 一个智能体 = LLM + tool calling + 执行循环 + 记忆/状态。 缺这四样，它只是个「提示词很长的聊天机器人」。
  • 起步用确定性自动化（n8n / Make）加一个关键节点上的 AI 调用，别第一天就做 100% 自主的智能体。出错面更小，也更好卖。
  • MCP（Model Context Protocol）是 Anthropic、Google、OpenAI 都在接入的标准，用来把智能体连到外部工具。今天学它，是真实的竞争优势，不是炒概念。
  • 别卖「我给你接入了 GPT-5 / Claude」。 卖 SLA：响应时间、问题解决率、每周省下多少人时。
  • RAG 仍然贡献着垂直智能体 80% 的价值。 知识库索引得好不好，比你选哪个模型更重要。
  • 没有可观测性（日志、追踪、评测）的智能体不是产品，是 demo。 按月付钱的客户需要看见「你也看得见智能体什么时候失败」。
  • 客单价最高的地方是「多智能体 + 与企业遗留系统（ERP、私有 CRM）深度集成」。 那里没有 no-code 搭建器能跟你竞争。
  • 从第一个客户起，就把 prompt 和流程当代码做版本管理。 今天躺在 textarea 里的提示词，明天就是生产环境里没人管得住的管线。

第 0 层：选任何工具之前，先看清零件

在卖任何东西之前，先把一个真实智能体的组成部件搞明白。

智能体循环。 智能体不是「一个会回答的提示词」，而是「感知 → 推理 → 行动 → 观察」的循环，一直转到目标达成，或者撞上步数上限。模型决定调哪个工具，工具返回结果，模型再决定下一步。没有这个循环，你手上只有聊天机器人。

Tool calling / function calling。 它让模型能执行真实代码：查 API、写数据库、发邮件。每个工具用一个 schema（名称、参数、描述）定义，模型靠它判断何时调用、怎么调用。

MCP（Model Context Protocol）。 这是 Anthropic 推动、Google 等已经采用的开放标准，作用是把工具和数据源以统一方式暴露给智能体，不必为每个模型重写一遍集成。如果你做的智能体要服务不止一个客户，学会用 MCP 暴露自己的工具，能省掉「换模型或客户换供应商时推倒重来」的那笔账。

记忆与状态。 短期是当前对话的上下文；长期是这个智能体对某个具体用户过往交互的记忆，通常存在向量库或键值存储里。没有持久记忆的智能体每次会话都问同样的问题，这是终端用户抱怨最多的一条。

RAG。 在智能体开始推理之前，它需要正确的数据。RAG 就是把客户的知识库（文档、FAQ、产品目录）索引进向量库，每次查询时检索相关片段注入模型上下文。分块（chunking）或嵌入（embedding）做得差，一个「技术上能跑」的智能体就废了。

选用例时，别按市场潜力选，按你的领域优势选。如果你已经懂某个行业（物流、医疗、法务）的实际作业流程，那就是你能设计出最好智能体的地方——因为你知道该问什么，也知道它可能在哪里出错。

先把可衡量的结果定下来，再谈架构。「我给你接个 AI 智能体」是卖不掉的。「我们把首次响应时间从 4 小时压到 2 分钟，并且在模型置信度低于 X% 时自动转人工」能卖掉，因为它有一个指标。

从第一个客户就开始收钱。一个「为了作品集」免费做的智能体，给你的不是生产环境反馈，而是 demo 反馈，这是两件事。

第 1 层：自动化 + 一次 AI 调用（这周就能收钱）

第一笔收入并不需要一个复杂的智能体框架。你需要的是「确定性流程（传统自动化）+ 一个由 LLM 完成的智能决策点」。

带意图分类的一线客服机器人。 webhook 收到 WhatsApp 或网页聊天的消息，LLM 用 function calling 判断意图（问价、查订单状态、投诉），再根据分类结果，让确定性流程去执行对应动作，或者转人工。典型栈是 n8n 或 Make 做编排、API 调模型做分类、接业务数据库拿动态答案。按响应时间 SLA 收月费。

带基础 RAG 的研究与摘要智能体。 面向律师、顾问、分析师：把他们的文档（判例、报告、合同）索引进一个简单的向量库，智能体回答问题时引用确切出处。这一层真正吃技术的地方是分块——法律文档的切片要保住「条 / 款」的上下文，而不是每 N 个 token 硬切一刀。

带打分的线索资格判定管线。 智能体在对话里问三四个结构化问题，用 structured output 或 JSON mode 抽出实体（预算、紧急程度、产品类型），算出一个分数，决定这条线索交给人类销售还是自动培育。好卖，因为 ROI 是直接可见的：销售团队少花时间在冷线索上。

基于状态触发的跟进智能体。 接上 CRM 或排期库，按记录的当前状态（而不是按一个盲目的定时任务）触发提醒、改约、售后跟进。这里的技术点是状态管理：智能体必须先读当前状态，再决定下一步做什么。

至于第一个客户怎么来：别去推销一个泛泛的「AI 智能体」。去一个具体业务里诊断一个可量化的瓶颈——响应时间、流失率、团队耗在重复任务上的小时数——然后提出解决它的那条具体流程。

第 2 层：从流程到打包产品

把同一类智能体在同一个垂直行业里做了几次之后，就该把它打包成可复用的技术产品。

带参数化变量的流程模板。 在 n8n 或 Make 里，把一个完整流程（webhook → LLM 分类 → 动作 → 日志）导出成模板，客户只需要填自己的 API 凭证和知识库。设计成本已经收回来了，后面每卖一份几乎是纯毛利。

垂直行业的 prompt 套件 + function calling schema。 系统提示词、few-shot 示例、函数 schema，都已经针对某个行业（房产、医疗、法务）调过、验过，打成 repo 或你所用工具的可导入集合。

按行业预构建的 RAG 知识库结构。 如果你已经为某一类数据（比如房产目录）解决了最优分块和元数据 schema，那这套索引结构本身就是产品，不只是数据。

关于你自己技术栈的迷你技术培训。 你是怎么搭出完整管线的（编排器 + 模型 + 向量库 + 可观测性），一步步写清楚。可以做成短课，卖给想搭同样东西、但不想走一遍试错曲线的人。

至于在哪卖：知识付费平台、带付费权限的私有 repo，或者在验证需求之前先手工交付，别一上来就投资做一套更复杂的东西。

第 3 层：自己会跑的系统（持续监控型智能体）

这一层的目标是「系统自己产生价值，不需要我每次手动触发一次执行」。它需要定时任务、事件触发，以及在没有人类持续盯着的情况下处理错误。

7×24 的监控告警智能体。 一个 cron 任务或事件监听器，跑一个智能体去检查信息源（竞品价格、品牌提及、监管变化），和上一次保存的状态作对比，只在出现实质变化时告警；并且在通知之前，先用 LLM 加一步校验，避免误报。按订阅收费。

自动化研究管线的 Newsletter 或频道。 抓取或调用 API 消费该领域的信息源 → 智能体做摘要并按相关性排序 → 你来过一遍、定角度，再发布。技术含量在摄入和去重管线，不在最后那一步写作。

智能体工具的技术测评账号（配联盟营销）。 自己搭基准，用同一批测试用例跑不同平台（n8n vs Make vs LangGraph、Claude Agent SDK 这类框架），公开方法论。技术上的严谨，是它和泛泛内容区别开的地方。

这一层最典型的技术错误：不记录失败的执行。系统无人值守地跑着，你就必须给自己留一条告警通道，否则发现问题的人会是你的客户。

第 4 层：深度集成（客单价就在这里）

这一层要求你理解客户那边的系统架构，而不只是会单独搭一个智能体。也是在这一层，一个客户可能值第 1 层的十个客户。

与遗留系统（ERP / 私有 CRM）集成。 遇到没有现代 API 的系统，有时得靠 RPA（界面自动化）配合 function calling，或者自己写一层中间件。这里 no-code 搭建器的竞争力会消失，因为问题是系统集成，不是提示词工程。

复杂流程的多智能体架构。 一个编排智能体把子任务派给专门的智能体（一个查数据、一个撰写、一个按业务规则校验），用 LangGraph、CrewAI 或 Anthropic 的 agent SDK 协调。真正卖得贵的是决策图的设计，以及部分失败时的处理。

面向智能体化的 AI 成熟度技术审计。 诊断一家公司现在哪些流程已经能用智能体自动化，哪些必须先做数据清洗或 API 暴露。交付物是一份带架构建议的实施计划，而不是一页点子清单。

以可观测性为形态的运维服务。 追踪看板（智能体调了哪些工具、延迟多少、错误率多少）、每次改 prompt 就跑一遍的回归评测、质量衰退告警。这是几乎没人当作独立服务在卖的经常性收入，因为它同时要求你懂 LLM 工程和 DevOps。

要进这一层，你不必是资深工程师，但你必须能读别人家的 API 文档、搞得清认证（OAuth、API key、签名 webhook），并且能推理分布式系统里的部分失败。

第 5 层：把它变成你自己的系统

当你有了一批客户，或者有一个自己会跑的产品，工作性质就变了：从「搭这个智能体」变成「让这套架构能复制，而且不只依赖你一个人」。

从第一个客户起，就把 prompt、schema、流程当代码做版本管理（用 git，不是 textarea）。「上周还好好的，现在我不知道出了什么问题」的头号原因，就是 prompt 没有版本控制。

建一套按垂直行业分类的内部模板框架，别每次重新设计架构。第一次花一周的事，第五次应该只花一天。

在感到产能饱和之前就涨价。如果你因为没时间而在反复修同样的 bug，说明之前那个价格已经太低了。

按客户核算真实成本（token 消耗、维护小时、事故次数）再对比收入，而不是只看毛收入。一个上下文吃得很多、又经常失败的客户，可能是比三个第 1 层的简单客户更差的生意。

最常见的技术错误

  • 把长 prompt 当成智能体。 没有 tool calling 和决策循环，就没有真正的自主性。
  • 不设步数上限和成本上限。 没有迭代上限的智能体会陷进循环里烧 token，直到账单出来才有人发现。
  • 等客户投诉才想起可观测性。 没有日志和追踪，排查生产故障就是猜。
  • 在结构上下文很重要的领域（法务、医疗、技术）用通用分块做 RAG。
  • 不对 prompt 和流程做版本管理，把它们当成一次性配置，而不是代码。
  • 对一个确定性自动化就能解决的问题，硬上复杂的多智能体架构。 不是所有事都需要自主性。

按类别分的工具栈

  • 模型与 API — Claude、GPT、Gemini 走 API，原生支持 function calling 与 structured output。
  • 智能体编排 — LangGraph、CrewAI，或各厂商自己的 agent SDK（如 Claude Agent SDK），用于有多个推理步骤的流程。
  • 无代码自动化（确定性那层） — n8n、Make、Zapier，把所有不需要推理的部分交给它们，LLM 只留在决策点上。
  • 工具协议 — MCP，让工具与数据在跨模型、跨客户时复用。
  • RAG 向量库 — Pinecone、Weaviate、pgvector，按数据量和「你栈里是不是已经有 Postgres」来选。
  • 持久记忆 — 专门做用户记忆的键值或向量存储，与通用知识 RAG 分开。
  • 可观测性与评测 — LLM 追踪工具（LangSmith 一类），记录执行、延迟、错误率；再加一套每次改 prompt 之前必跑的回归评测。
  • 版本控制 — git 管 prompt、函数 schema、导出的流程，而不是一个散落的文档。

结尾

上面这些层级，没有一个要求你是机器学习工程师。它要求的是：你对架构的理解足够深，能诊断准确；你选一个自己本来就有领域优势的用例；你用指标去销售，而不是用「AI」这个词。

这周就从第 1 层开始：一条确定性流程，一个由 LLM 做决策的点，可衡量，第一天就收费。

译者后记

三点使用说明。

一、这是一份「卖智能体」的商业路线图，不只是一份技术教程。 六层阶梯里真正稀缺的不是前三层的实现能力，而是第 4 层那种「能读懂客户遗留系统」的工程判断力。原文面向的是西语圈的自由职业者和小团队，价格与获客路径都基于那边的市场；搬回国内要换算——很多企业更习惯项目制验收，而不是按月付 SLA，这会影响你在第 1 层和第 2 层之间的定价方式。

二、文中的产品名按原文照译，未逐一核实。 「Gemini Spark」「GPT-5」这类命名，以及「OpenAI 已接入 MCP」的表述，都是原文写下的时点状态，工具栈部分也带有明显的 2026 年生态痕迹。真要照着选型，建议以各家官方文档为准。

三、如果要我只留两句，我会留第 0 层和第 5 层。 第 0 层说清了门槛：没有执行循环和工具调用，你做的就不是智能体；第 5 层说清了工程底线：prompt 不做版本管理，等于没有工程。中间那四层是商业路径，可以按自己的处境跳着走，但这两头跳不过去。

另外补一句原文没提但值得放在心上的：爬阶梯时最容易犯的错是跳级——第 1 层还没收到过钱，就先去做第 4 层的多智能体架构。大多数失败的项目不是技术不够，是卖的东西没人愿意付钱。
